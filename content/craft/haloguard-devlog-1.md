# HaloGuard 开发日志 #1 — 树莓派上位机系统架构复盘

> 做完一个项目最大的收获不是代码，是架构决策背后的思考过程。

## 项目背景

HaloGuard 是一个桌面陪伴机器人项目——能看、能听、能说、能动。它有一个摄像头用于视觉感知，一个麦克风阵列用于语音交互，一个小触摸屏用于状态显示，底盘有两个驱动轮和一个舵机控制的"头部"。

这是我第一个涉及多个硬件模块协同工作的项目。之前写代码都是纯软件，最多调个 API。突然要处理摄像头、麦克风、电机、串口通信、AI 推理这些东西同时运行的场景，一开始是真的懵。

## 整体架构

经过反复推敲，我最终选了一个**双层架构**：

**上位机：树莓派5**
负责"大脑"层面的工作——视觉处理（OpenCV + YOLO）、语音识别（Whisper）、对话生成（调用大模型 API）、触摸屏 UI、以及总体的行为决策逻辑。树莓派跑的是 Python，因为 AI 相关的库生态基本都在 Python 这边。

**下位机：ESP32**
负责"小脑和肢体"——读取传感器数据（红外避障、超声测距）、控制底盘电机（双 H 桥驱动）、控制舵机（头部转向）。ESP32 跑的是 C++（Arduino 框架），因为实时性要求高、硬件交互多。

两者之间通过**USB 串口**通信。树莓派发指令，ESP32 执行；ESP32 上报传感器数据，树莓派做决策。

为什么不全放在树莓派上？因为树莓派跑 Linux，不适合做硬实时控制。Linux 内核不是实时操作系统，你没法保证每 10ms 精确执行一次电机 PID 循环。ESP32 跑裸机或 FreeRTOS，定时中断是稳的。

## 模块划分的思考

上位机这边，我把功能拆成了几个独立模块：

- **视觉模块（vision）**：摄像头采集 → YOLO 检测 → 输出目标位置
- **语音模块（voice）**：麦克风采集 → VAD 端点检测 → Whisper 识别 → 输出文本
- **对话模块（chat）**：接收文本 → 调用大模型 API → 输出回复 → TTS 播放
- **行为决策模块（brain）**：整合视觉和语音信息 → 决定下一步动作 → 发串口指令
- **UI 模块（display）**：触摸屏显示状态、表情、对话内容

为什么要这样拆？最直接的原因是：**视觉和对话必须解耦**。

一开始我犯了一个错误，试图把"看到人 → 打招呼"这个流程写成一个长函数：调摄像头、跑检测、判断是否有人、生成对话、播放语音、控制头部转向……全在一个 while 循环里。结果发现，YOLO 推理要 200ms，大模型 API 调用要 2-3 秒，期间整个系统都卡住了，摄像头不采集、电机不响应。

解耦之后，每个模块跑自己的线程（或进程），通过消息队列通信。视觉模块持续检测不停顿，语音模块持续监听不等待，对话模块异步调 API 不阻塞。各模块之间只传递简短的消息（"检测到人脸，位置 x=320, y=240"、"用户说了：你好"），不共享状态。

这让我第一次深刻理解了"模块化"不是代码整洁度的问题，是系统能不能正常工作的问题。

## 串口通信协议

树莓派和 ESP32 之间的串口通信协议是我自己设计的，很简单但够用：

每条指令是一个固定格式的帧：

```
[帧头 0xAA] [指令类型 1字节] [数据1 2字节] [数据2 2字节] [校验和 1字节] [帧尾 0x55]
```

指令类型举例：
- `0x01`：设置左右轮速度（数据1 = 左轮PWM, 数据2 = 右轮PWM）
- `0x02`：设置舵机角度（数据1 = 舵机编号, 数据2 = 角度）
- `0x03`：查询传感器（数据1 = 传感器编号）
- `0x10`：ESP32 上报传感器数据

校验和是除帧头帧尾外所有字节的异或值。

这个协议很原始，没有重传机制、没有流控、没有消息确认。但在 USB 串口 115200 波特率、指令频率 20Hz 的场景下，丢包率极低，暂时够用。以后如果换成无线通信（蓝牙/WiFi），就需要更健壮的协议了。

## AI 辅助开发的真实体验

这里我想坦诚地说一件事：HaloGuard 项目中，很多模块的底层代码是借助 AI 生成的。

比如 YOLO 推理的 Python 封装、Whisper 的流式识别、串口通信的 Python 端实现、ESP32 的电机驱动代码——这些我都是先描述需求，让 AI 生成初版代码，然后我逐行阅读、理解、修改、调试。

但系统设计、集成调试和问题诊断是我自己完成的。

"为什么要用双层架构"——这个决策 AI 没法替我做，因为它不知道我的硬件条件和实时性需求。"视觉模块卡住整个系统"——这个 bug 是我在联调时发现的，AI 没法帮我调试一个涉及多个硬件的时序问题。"串口协议为什么这样设计"——这个是我根据带宽、延迟、可靠性的权衡做出的选择。

我的工作模式是：**我把系统架构想清楚，让 AI 帮我实现每个模块的代码，我负责集成和调试。**

有人可能会质疑这算不算"真正会写代码"。我的看法是：在 AI 时代，理解系统架构比手写每一行代码更重要。就像一个导演不需要亲自演每个角色，但他必须理解每个角色的作用和它们之间的关系。关键是你能不能在系统出问题时定位到是哪个模块、哪个接口、哪个时序出了错——这个能力，AI 给不了你。

## 还不完善的地方

- 异常处理很粗糙，串口断开后没有自动重连机制
- 没有日志系统，调试全靠 print
- 行为决策是硬编码的 if-else，没有状态机或行为树
- 功耗没有考虑，树莓派5 + 摄像头 + 屏幕跑满功率有点热

这些后面慢慢迭代。第一版能跑通完整流程就行，别追求完美。
